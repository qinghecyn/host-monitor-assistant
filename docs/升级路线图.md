## 一、现状盘点（为什么是这四块）

| 现状 | 问题 |
|---|---|
| 告警只有界面横幅 | 人不在屏幕前 = 没有监控 |
| 历史只有 5 分钟内存环形缓冲，重启清零 | 回答不了"上周三 CPU 是不是飙过"，做不了容量规划 |
| 桌面版跟着窗口走、手机版 App 被杀就停 | 监控者自身无守护，自己挂了没人知道 |
| 只看资源（CPU/内存/磁盘/温度） | 业务可用性（端口/网站活没活）完全看不到 |

## 二、beta2.2 —— 运维核心包（四个模块）

### ① 告警推送

**做什么**：阈值/事件触发时推送到外部通道，让告警能"叫醒人"。

**设计要点**

- 通道：Server酱（微信，最省事）/ Telegram Bot / SMTP 邮件 / 通用 WebHook（钉钉、企微都能套），多通道可同时启用，每通道可勾选接收哪些告警级别
- **去重收敛**：同一告警（同主机+同 kind+同 zone）在静默期内只推一次，默认 10 分钟，可配
- **恢复通知**：告警解除后推"✓ 已恢复"，正文带持续时间——恢复通知和告警本身同等重要
- **静默时段**：按星期 + 时段免打扰（如 02:00-06:00），维护窗口用
- 推送失败重试 3 次指数退避，失败记 server.log，不阻塞采集主循环（后台队列）

**涉及文件**

```
server/alerts.py        evaluate() 结果由"每帧重算"改为"边沿触发"（新增/恢复事件）
server/notify.py        新增：通道适配 + 收敛去重 + 静默时段 + 发送队列
server/config.py        [notify] 段：channels / dedup_minutes / quiet_hours
web/                    设置面板新增"告警推送"区（通道表单 + "发送测试消息"按钮）
tests/                  事件触发、去重、恢复、静默时段单测
```

**验收**：真实拔网线/打满 CPU 触发告警 → 微信收到通知 → 解除后收到恢复通知；同一告警 10 分钟内不重复。

### ② SQLite 历史落盘 + 趋势查询页

**做什么**：每帧指标写入本地 SQLite（数据目录 `history.db`），默认保留 90 天，可在设置里改 7~365 天。

**设计要点**

- 表结构：`samples(ts, host, metric, value)` 长表 + `docker_events`（容器起停事件，顺手记）
- 写入走后台批量事务（攒 5 秒一批），绝不拖慢采集主循环；WAL 模式
- 每小时清理过期数据（保留天数可配）；`history.db` 单文件，直接复制即备份
- **趋势页**：前端新增"历史"入口——任选主机 / 指标（CPU、内存、温度、风扇、上下行、Docker 容器数…）/ 时间范围（近 1 小时 ~ 近 90 天）画曲线；后端 `GET /api/history?host=&metric=&from=&to=` 自动按密度降采样（范围越长粒度越粗，保证返回点数 ≤ 800）
- 内存 5 分钟环形缓冲保留不动（实时曲线不走数据库，零回归风险）

**涉及文件**

```
server/store.py         新增：SQLite 读写 + 降采样查询
server/app.py           on_frame 挂钩写库；lifespan 里起清理任务
server/api.py           GET /api/history
web/                    新增"历史"页签（复用 charts.js）
config.py               [history] keep_days
tests/                  写入/查询/降采样/清理单测（临时库）
```

**验收**：跑一小时后能在趋势页选"昨天"看曲线；重启服务历史不丢；库文件增长速率可预期（约 5~10MB/天/主机）。

### ③ Windows 服务 + 自监控心跳

**做什么**：桌面版后端注册成 Windows 服务，开机自启、无窗口、崩溃自动拉起；监控自己"死亡"时也能告警出去。

**设计要点**

- 用 **WinSW**（或 sc + 现有 exe 包一层）把 `xiaozhushou-server.exe` 注册为服务 `XiaozhushouMonitor`；桌面壳（Tauri 窗口/托盘）保持可选——服务在后台跑，开窗口只是"看"
- 安装包 NSIS 里加"注册为系统服务"勾选项（默认勾选）；卸载时反注册
- **心跳自监控**：服务每分钟向已配置的推送通道发心跳——推不出去或进程死了，用户在外部通道侧发现"心跳断了"（配合 Server酱的"不再提醒则异常"或 Uptime 接收端即可形成死信检测）
- 服务模式下日志仍写 `<data-dir>\server.log`（滚动）

**涉及文件**

```
packaging/nsis-services.nsh   新增：服务注册/反注册宏
server/heartbeat.py           新增：心跳发送
web/                          设置面板加"开机自启（系统服务）"开关（调后端新增的 /api/service 端点）
```

**验收**：重启 Windows 不开任何窗口，服务在跑、`/api/ping` 通、托盘可随时唤出界面；任务管理器杀进程后 30 秒内被拉起。

### ④ 服务拨测（业务可用性）

**做什么**：主动探测任意目标的 TCP 端口 / HTTP(S) 可用性 / ICMP ping，失败走告警推送——监控从"机器资源"扩展到"业务活没活"。

**设计要点**

- 监控机直接发起（**不需要 SSH**，和资源采集是两条独立管道），可加任意 IP:端口，比如路由器的 443、NAS 的 445、内外网网站
- 类型：`tcp`（连得上即活）/ `http`（状态码 < 500 即活，可配期望码/关键词）/ `ping`
- 参数：间隔（默认 30s）、超时（默认 5s）、连续失败 N 次才算告警（防抖，默认 2）、恢复通知——复用 ① 的事件与推送管线
- 拨测结果同样落 SQLite（②），趋势页可画可用率；界面上每条拨测一个状态点（绿/红 + 延迟 ms）
- 拨测并发执行（asyncio，单机几百条无压力）；单条失败不影响其他

**涉及文件**

```
server/probes.py        新增：拨测执行器（asyncio.open_connection / httpx / ping 子进程）
server/probes_config.py 拨测项 CRUD（[probes.*] 段，config.toml 原子写复用现有机制）
web/                    新增"拨测"页签：列表 + 状态 + 增删改
tests/                  三类探针 + 防抖 + 恢复单测（本地起测试端口）
```

**验收**：添加一条 `tcp 192.168.1.100:443` 拨测 → 停掉对应服务 → 收到告警 → 恢复后收到恢复通知；趋势页能看到可用率曲线。

## 五、1.1 及以后（排队）

| 模块 | 内容 | 备注 |
|---|---|---|
| 进程监控 | 每主机 CPU/内存 Top 进程（SSH `ps` 采集，协议新增 PS 段）、指定进程存活检测 | 套路照抄风扇的"加采集项五步法"（开发文档第九节） |
| 磁盘容量预测 | 基于 SQLite 历史做线性回归，"按当前涨法还能撑 N 天"，<30 天提前告警 | ② 的直接收益 |
| 多用户 | 只读访客角色（看大屏不给改配置权限） | `[auth]` 加 roles |
| 手机本地通知 | App 存活期间告警弹系统通知（Android Notification） | android 分支加 Java 桥 + POST_NOTIFICATIONS |
| 安卓前台服务 | 退后台后强保活（dataSync 类型前台 Service） | targetSdk 36 需声明权限与类型 |
| SNMP | 纯交换机/AP 等无法 SSH 的设备 | 独立采集管道 |
| Windows 目标机 | SSH 到 Windows 采样（typeperf/powershell） | 工作量大，慎重排期 |
| 开放 API | 只读 API key 供第三方拉数据 | 需求出现再做 |
